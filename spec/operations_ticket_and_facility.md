# 运营工单执行清单与设施问答

关联 REQ-03/06/07/08/12/13。延续 [服务可靠性](service_reliability.md) 和 [酒店服务完善](hotel_readiness.md)，不更换入住授权、模型或单写入者架构。

## OT-01 · 员工可执行的物品明细

运营中枢的每张送物单必须展示标准物品名称、单位、申请数量、已预留数量、当前可用数量、缺口及是否需要补货。原始需求单独标注，不能代替执行清单。多条工单各列自己的明细；当前无法可靠拆解的多物品一句话继续澄清，不能只取最后一个物品派单。

由共享只读函数 `delivery_fulfillment(ticket, inventory)` 计算 `fulfillment`；本地和 API 工作台使用同一契约。API 仅在员工工单/运营接口投影，不向住客暴露酒店全局库存。缺口为 `max(申请数量 - 已预留数量 - 当前可用数量, 0)`；已预留且可用库存为 0 的订单仍可正常派送，不能重复扣库。

旧工单缺少结构化字段、含未核验物品或与明细冲突时，标记“待人工核验”，不凭原文猜出完整有效清单。保留原工单/审计，不自动删除或补扣库存。住客原文与动态字段必须安全转义，不能作为可执行 HTML。

## OT-02 · 缺货与派送分离

已知物品超库存可保留库存协调申请，必须明确“待库存协调，未确认派送”，不能显示为可派送，不给送达承诺；新申请的 `delivery_status` 为 `待库存协调`。需求、现有库存、缺口和补货建议同时可见。库存回升但尚未足额预留时显示“待库存预留”，不能自动宣称已补货、已预留或开始配送。

前端禁用不合格的派送/完成操作，后端仍须拒绝缺少足额预留、旧错误明细或待确认变更的派送/结单。正常改数量/换物品成功后重新计算展示，不沿用旧缺口；取消后不再显示补货建议。此次不新增采购、收货或自动补货系统。

多张送物单并存时，“吹风机改成3个”“水改成1瓶”等变更标记之前的物品名可定位对应原单；同种物品有多张原单仍须澄清具体单号。只有新物品名的“改成3个吹风机”不能擅自选原单。缺货协调申请改单成功并足额预留后才转为待派送，其他工单数量和库存保持不变。

## FQ-01 · 按问项回答

依据已配置知识识别设施与问项：地点、开门/开始、关门/结束、开放时段、费用/预约、是否提供。若配置为 06:00–23:00，问“健身房几点关门”应直接答“健身房 23:00 关门”；只问关门不重复完整开放时段。位置、开/关时间、收费没有可信配置时逐项说明待核验，不从旧 standard 夹具填入 academic 配置。

同轮涉及足浴/洗脚/按摩与健身房，必须各有答复；同轮各设施的时间/地点不得串用。多问项、标点变化、同义词、否定句、故障与送物混合场景均需回归。纯咨询不创建送物/预约单；服务咨询不能吞掉同轮取消、送物或安全报修。

## 验收

- 工单：足额预留、已预留后可用为 0、库存不足、零库存、库存回升未预留、取消/配送/送达/变更中、旧字段缺失、旧混合未知物品、改数量/换物品，逐项断言明细及按钮权限；后端同类操作拒绝且无额外扣库。
- API：员工工单和运营状态投影一致；部门过滤保持；住客无库存视图；持久化重启后投影不丢失、不篡改原记录。
- 问答：至少 48 条有编号变体，分组报告断言和失败；同时覆盖 standard 已知配置、academic 未核验及自定义设施配置。不得以单一通过率替代逐条语义断言，不声称穷尽自然语言。
- UI：本地和 API 卡片均有具体清单、状态、补货信息；1280×720 及窄屏可阅读；执行清单原生 `st.text` 的内部 span 在三种主题下同样使用主题文字色，浏览器实测对比度至少 4.5:1，不能只检查外层容器；旧错误工单与缺货单无可用派送/结单按钮。原始截图、焦点 RED/GREEN 和完整发布验证放 `.artifacts/`，由最终证据文档引用。
