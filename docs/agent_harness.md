# 这个项目的 Harness 底座

Harness 是让模型能够持续、受控地完成任务的外围运行系统。模型负责理解和提出下一步；Harness 管理它能看到什么、能调用什么、任务执行到哪、何时中断、结果怎样落库，以及出错后如何定位。

在本项目中，一句“送两瓶水，再拿三条毛巾”会经过以下过程：

1. 根据当前入住凭证确定会话、房间和权限，不用聊天自述授予权限。
2. 模型一次输出结构化理解和逐字来源片段，程序验证片段、物品与数量；无效提案回到现有解析或澄清。
3. 运行时创建带版本的任务，在快照内调用对应部门处理器；部门只能提交提案。
4. 主控核验库存、工单、权限与最新任务版本，再原子提交。用户中途取消，过期 worker 的结果不能覆盖最新需求。
5. 保存消息、业务状态和执行记录，回复使用实际提交的结果；连接失败与规则处理分别显示。

## 代码对应

| 底座职责 | 当前实现 |
| --- | --- |
| 模型连接、超时、输出限制、调用诊断 | `hotel_core.py::OpenAICompatibleClient`；硅基流动 Qwen3 使用非思考模式，12 秒请求超时、零隐式重试 |
| 需求理解与可校验的动作提案 | `ReceptionAgent`、`semantic_intents.py`、`guest_requests.py`；模型拆句，程序核验来源与业务参数 |
| 工具与能力边界 | `hotel_core.py` 部门处理器、`agent_protocol.py`；未接入的客房远程控制明确说明不支持 |
| 会话上下文与完整归档 | `HotelState`、`agent_runtime.py`、`persistence.py`；短上下文与完整记录分层，会话称呼偏好独立于登记身份 |
| 异步执行、中断、并发与幂等 | `SessionManager`；会话队列、任务版本、取消代际、共享库存和提交前校验 |
| 身份与岗位权限 | `auth.py`、`server.py`；room/stay/session/grant 校验，模型不能授予权限 |
| 持久化、回滚和审计 | `persistence.py`；SQLite、单写入者、原子检查点 |
| 可观测性 | 任务状态、`last_trace`、模型 `last_probe/last_call`、错误码与耗时 |

本地 Streamlit 是内存工作台；受保护部署的唯一业务写入者是 API。侧栏切模型只替换客户端，保留原会话、工单、库存和归档；运行中先完成或取消任务。

## Runtime Harness 与 Evaluation Harness

上面的执行系统属于 **runtime harness**。**Evaluation harness** 是评测装置：准备输入与预期，实际运行系统，断言工单、库存、取消、权限和回复，再输出指标与失败记录。本仓库对应 `harness/eval_runner.py`、固定 H01–H20、分层质量集和 `scripts/verify_release.py`。

“跑一个小测试看看回复”只是一次冒烟检查。完整评测还要检查实际业务状态、失败情况、并发竞态和重复执行，不能只看回复像不像正确答案。

ReAct、Plan-and-Execute 是模型组织推理与行动的方式；多 Agent 是职责拆分方式。它们可以由同一个 Harness 调度。Harness 不是某个模型，也不要求一定使用多 Agent。

## 修复难例与自更新的边界

Bad case 可以帮助发现错误。经脱敏和审核后，将代表性例子加入 Few-Shot 库，或修改提示、检索、解析和执行机制，再用未参与修改的回归样本验证。这是在更新外围系统；没有训练模型权重，就不属于模型微调。

当前 `harness/self_evolution.py` 提供按字符相似度选择示例的动态 Few-Shot；没有自动证明效果提升，也没有无人审核的自训练闭环。要声称提升，须固定旧版与新版、保留独立测试集，并比较逐项业务指标与失败样例。

## 本次语义能力的范围

模型可以提出无标点复合需求的分项方案，并在同一 JSON 中给出合规短答，减少重复请求。物品标准名与数量仍须通过现有目录和解析验证；任意新别称、复杂否定或共享数量不能保证一次理解成功，无法核验就澄清。高风险投诉、身份、取消和库存提交继续由程序约束。
