# 学术酒店详细业务规格

上级：[主规格](../specification.md)。配套：[架构](architecture.md)、[实验](../experiments.md)、[验收](../acceptance_criteria.md)、[追溯](../traceability.md)。本文件描述代码边界；正式政策须学校批准，现场状态为 `NOT_VERIFIED`。

## 身份与岗位

对应 REQ-01、REQ-02。前台先在系统外核对接待订单与身份，再提交 `identity_checked=true`；此值记录员工声明，不是学校身份系统自动认证。

1. 前台/经理/管理员登记在住并签发凭证；非在住、无核验或无权限拒绝。
2. grant 绑定 grant_id、session_id、room_no、stay_id、expires_at；住客 Bearer 凭证有 HMAC 签名。默认 86400 秒，允许 60 秒至 7 天。
3. 请求先验签名/过期，再验 grant 未吊销、在住状态及当前 stay；住客只见本次入住会话记录。
4. 新入住生成新 stay 并吊销旧 grant；有处理中工单时须先结清原服务。旧在途任务提交前再次校验身份。
5. 过期/吊销/换客旧凭证 401，跨会话/跨房/越权视图 403。

| 身份 | 读写边界 |
| --- | --- |
| guest | 本会话聊天、任务、进度、归档；不能访问全店工单或审批 |
| frontdesk | 核验、签发/吊销、入住登记、延退、夜审及冲突核验；运营业务 |
| housekeeping / engineering | 所属部门工单办理；房态仅 room_no、room_status、checkout_time，私聊与历史拒绝 |
| manager | 人工审批、运营及审计查看 |
| admin | 配置的独立随机管理员凭据 |
| local | 关闭鉴权的开发身份，不能作为部署授权证据 |

API 是授权边界，隐藏按钮不替代授权。当前为本地岗位令牌映射，尚无学校 SSO 或外部身份源联调。

## 接待与补槽

对应 REQ-03、REQ-04。接待先规则识别，可用云辅助，最终仍受业务护栏与提交约束。住客自称会员、模型猜测房号不能授予权益。

- 多主题 FAQ 按主题去重并与服务结果合成；缺槽或写操作不能吞掉咨询回答。
- academic 早餐地点/时间、签到等未知政策联系前台或会务，不用 standard 固定政策填空。
- 当前类型：送物、工程、客诉、延退、续住、票券；是单服务和 FAQ 融合，不保证一轮执行任意多个写请求。
- 开发会话可保存 pending 后问房号或时间；未知在住不臆造。已认证房间由凭证绑定，“切换”文字不能改绑。
- 送物多个物品、歧义或零数量先澄清；多单取消/替换先定位。完成信号不作为新工单。
- 回复区分“已提交申请”“需核验”“待派送”与实物完成；HTTP 200 不能替代业务状态。

## 学术接待待遇与人工核验

对应 REQ-11。两套 profile 不混用：

| 业务 | academic | standard 兼容夹具 |
| --- | --- | --- |
| 延退 | 前台核对接待订单、房态和会务排期；审批前保留原时间 | 在住黑金、12:00 后且不晚于 14:00、房态充裕、无冲突早到排期可自动批准 |
| 早餐券 | 礼宾记录需前台核验，实际办理由前台承担 | 有效在住模拟台账累计不超 4 张可显示已发放，不是真实券 |
| 费用 | 按接待订单和前台确认，不能自动免费承诺 | 保留商业演示权益文案 |
| 未知政策 | 联系前台/会务核验 | 固定知识只用于演示回归 |

延退须合法时间且晚于 12:00；超过 14:00、房态紧张、无在住等人工审核。申请带 request_id、stay_id、owner_session_id，同一当前申请可复用。员工须带 expected_request_id，缺标识 400，旧入住或过时申请拒绝。批准后更新本地 PMS 并通知申请所属会话；拒绝/撤回按实现重置申请和时间，不代表外部同步。

餐券约束：

1. “给我两张早餐券”“给房间发两张早餐券”“给1128发两张早餐券”“送两张早餐券到房间”及已知早饭券/餐券/体验券进入礼宾核验。
2. 正常请求新增 `需前台核验` 记录，抽取数量，提交时绑定房间/session/stay；Trace 含 `issue_breakfast_vouchers`。不建保洁单、不扣券库存、不承诺已发放。
3. 保洁直接 dispatch 票券在库存操作前抛 AgentConflict；编排器可记录待人工冲突，不能提交送物副作用。
4. 已存在送物“改成两张早餐券”保留原单和库存，提示前台核验；直接 revise 同样拒绝，不生成改券成功或待确认券变更。
5. 当前无电子券签发/核销/审批接口和订单额度对账。未知票券别名、跨系统额度及迁移前脏数据不在本次修复证明范围。

完整测试点名由 [机器追溯](../traceability.json) 维护，焦点原始日志位于 `.artifacts/verification/task1-coupon/`。

## 送物生命周期

对应 REQ-05、REQ-06。保洁按物品与数量预留库存；ETA 是规则估计，不是酒店承诺或生产时延。合成初始毛巾/浴巾各 24、早餐券 40，不能当作真实库存。

| 状态 / 输入 | 动作与结果 |
| --- | --- |
| 新送物且足量 | 处理中/待派送工单，预留数量 |
| 库存不足 | 不预留，记录协调，回复尚未确认派送 |
| 待派送改物/数量 | 原 ticket_id，释放旧量并检查新量，足量才预留；不足保留原单 |
| 待派送取消 | 已取消，释放预留；“水不用了”只定位水单 |
| 配送中/已送达变更 | 独立 change_id、待部门确认；保持旧物品/预留，不立即承诺取消成功 |
| 部门确认 | expected_change_id 匹配；重复不重复扣库，旧 ID 拒绝，拒绝维持原业务 |
| 多单指代不明 | 澄清，不修改任何单 |
| 住客确认完成 | 同步完成不建重复单；待变更期间不能抢先结单 |

雨伞、充电器、吹风机登记借用。已送达退回需 returned=true，回收量进入 quarantine 待检，不直接恢复可用库存。异步取消/改物保持 task_id 和递增 version；旧 worker 不得提交。受控竞态正确性不等于现场容量。

## 工程、客诉与续住

对应 REQ-07。工程默认中；重大险情或愤怒为高、红色。明确严重客诉走大堂经理/高/红色；普通生气伴随故障仍保留工程责任。安全建议与“10 分钟回访”为内部模板/目标，没有已联调短信电话保障。

续住需有效在住；礼宾提交前台申请并注明晚数和房态。房态充裕也需前台确认续费/房卡，不能自动扣款或声称外部 PMS 已续住。补偿建议也不是发放授权。

提案违反物品/数量/房号/部门/风险/库存，记录 agent_conflicts 和 needs_review，不派单不扣库。人工标记已核验只处理冲突记录，不自动生成被拒工单，须重新发起合法业务。

## 部门回执与夜审

对应 REQ-12。API 部门操作和住客通知共用运行时与持久化，派送/变更/结单由所属岗位办理，已收到申请不能显示为实物送达。

夜审携带 expected_date，同一旧日期首次成功后再次拒绝；新业务日、房态和台账持久化。已落库日期优先于环境初始日期；旧 worker 不覆盖夜审变化。合成台账推进不能解释为学校财务日结或外部 PMS 夜审。

## 故障与验收边界

对应 REQ-08…REQ-10、REQ-13…REQ-16。同 session + request_id + 相同载荷复用 run，重启/裁剪后仍幂等，改载荷拒绝。写故障撤销副作用，聊天可 HTTP 200 且 run_status=failed；员工故障及 /ready 可为 503。客户端须检查业务状态。

短期黑板与归档历史分层，裁剪仍可分页，换客不能读前一入住消息/单/进度。数据保留期限、正式脱敏与恢复演练须学校确认。[实验](../experiments.md) 定义时序、断言和清理，现场未执行须保留 TARGET_NOT_RUN。
