# 酒店 Multi-Agent 项目：面试逐字稿

更新：2026-10-20。引用框可直接口述，每题按自己的语速练习。内容对应当前本地 Demo；PMS、住客和工单均为模拟数据。

## 项目介绍：约一分钟

**记忆线：酒店服务 → 角色分工 → 需求变更 → 规则把关 → 回归验证。**

> 这是我开发的智慧酒店服务 Demo，主要解决住客问询和服务申请需要前台反复转交的问题。我负责 Python 业务核心、部门协同和离线评测。系统由接待层理解需求、补齐房号，再交给保洁、工程、礼宾或经理处理，通过黑板衔接任务和工单。后续我补了处理中继续输入、取消和改单，比如先要毛巾又改要浴巾，会让旧版本失效，避免旧结果继续建单；已经配送的要等部门确认撤回。模型可以辅助理解，业务写入仍由规则核验。目前使用模拟的 240 间客房，96 项测试和 20 条离线场景通过，还没有接真实酒店系统。

## Q1：为什么用多 Agent，不用单 Agent？

**记忆句：共享数据，划分职责，权衡成本。**

> 单 Agent 加工具也可以完成这个项目。我采用角色分工，是为了让接待、保洁、工程等部门的规则和处理结果更清楚，便于分别修改和测试。黑板负责信息衔接，角色负责各自的业务。简单业务我会优先考虑单 Agent，因为多角色也有协调成本。当前没有对照实验，不能说多 Agent 一定更准确或更省 token。

## Q2：既然共享记忆，换几个 Skill 不就行了吗？

> Skill 可以理解成可复用的操作规范或能力模块，单 Agent 可以按需要加载不同 Skill。是否拆成多个 Agent，要看是否需要独立的职责、状态、权限和执行控制，不能只看 Prompt 不同。我的项目目前主要是部门业务模块协同，没有每个角色都独立自主规划；用单 Agent 加模块化工具重构也是可行方案。

理解：LLM 加一份 SOP 不会自动获得执行能力，还需要程序负责调用工具、保存状态、检查结果和停止条件。Skill 的具体能力取决于系统实现，不宜把所有 Skill 都定义成纯文本 SOP。

## Q3：Agent 之间具体怎么协作？

**记忆句：接待提需求，部门出结果，主控查规则，黑板接状态。**

> 接待层先提取需求，缺房号就追问。编排器读取当前状态，调用对应部门，部门返回结构化工单提案。主控核对房号、物品、数量、部门、风险和库存，符合规则才提交，并把进度写回黑板。共享状态不等于每个角色都能随便修改，也不需要把全部历史交给每个角色。

## Q4：主 Agent 和子 Agent 判断不一致，听谁的？

> 不按主子身份判断真假。用户最新有效需求决定要做什么，可信工单、库存和安全规则决定能不能做，主控统一核验和提交。比如用户要浴巾，部门却返回毛巾，就拒绝提交；如果部门记录已经配送，就不能按旧计划直接取消。无法核验的情况记录冲突，转人工确认。

## Q5：子 Agent 还没处理完，用户又改需求怎么办？

**记忆句：辨关系、升版本、查提交、看执行阶段。**

> 先区分修改原任务和新增问题。毛巾改成浴巾时，更新原任务版本，让旧执行失效；提交工单和扣库存前，再检查是不是当前有效版本。旧执行即使晚返回，也不能提交或发送旧的成功回复。如果只是顺便问早餐，就保留原服务，按序处理。这里考的是异步中断，也包括状态一致性和业务补偿。

补充：当前用后台线程和协作式取消，不能强行停止已经发出的模型请求；保证的是过时结果不能提交，未测得具体 token 节省。

## Q6：已经派送了，还能直接取消吗？

> 要按执行阶段处理。待派送可以修改原工单，释放旧物品库存预留，再预留新物品。配送中就先记录变更，等部门确认能否撤回；已经送达还要确认物品是否取回。确认前不能告诉住客取消成功。当前运营页提供确认或拒绝变更，并把结果通知原会话。

## Q7：“水不用了”现在为什么能识别？用了大模型吗？

**记忆句：模型可选，当前取消靠规则和工单状态。**

> 项目可以用模型识别意图、房号和情绪，但当前取消对象的定位由程序规则和工单状态完成。之前“水不用了”失败，是物品别名没有统一到“矿泉水”，多个工单时就没找到对象。现在将常见饮用水表达归一化，同时保护“热水”“漏水”等其他含义。只有一句“不用了”、又存在多个候选工单时，仍会追问，避免取消错单。

当前模型输入没有完整历史和当前工单列表，不能说本次修复验证了 LLM 的上下文理解或泛化能力。

## Q8：Memory 到底怎么存？黑板就是短期记忆吗？

**记忆句：消息放列表，业务放字段，长期另做持久化。**

> 当前会话由 session_id 对应一个状态对象。消息放 Python 列表，房号、待办、任务版本分别放结构化字段。超过十二条消息会保留最近六条，并生成截断摘要，但摘要还没有送进模型理解调用。黑板主要保存协作中的业务状态，可以看作工作记忆的一部分，不只是聊天记录。现在数据在内存里，没有实现隔天或重启后的长期恢复。

若被问“以后怎么做”：

> 我会用数据库存原始消息、任务和审核后的长期信息，按租户、用户和会话关联，日期用于分区或查询。用户隔天回来时，先验证身份，再查询未完成任务、近期摘要和相关历史，按需要组装上下文。session_id 负责会话标识，不能代替身份认证；也不能只靠昨天的 session_id 找回跨会话记忆。

这是后续设计，没有接入当前 Demo。时间分区是存储管理方式，不能单独证明已经实现长期记忆。

## Q9：除了 ReAct、Memory，LLM 外围还要设计什么？

**记忆线：目标、执行、上下文、工具、知识、权限、恢复、评测。**

> 除了目标和角色提示，还要有执行控制、上下文与记忆、工具参数和结果检查、知识检索、权限审批、失败重试，以及日志和评测。我的项目尤其补了任务版本、请求去重和共享库存提交检查。ReAct 是执行模式，Memory 是组件，它们不能覆盖全部工程问题。

## Q10：除了 Multi-Agent，还了解什么模式或框架？

> 我会区分模式和开发工具。ReAct 是判断、行动、观察结果后继续；Plan-and-Execute 是先拆计划，再执行并按结果调整。具体框架方面可以介绍自己确实了解或用过的工具，并说明使用程度。我的项目核心用 Python 自行实现，没有接入通用自主规划框架，不能把知道名字说成有落地经验。

“Multi-Agent”是协作架构，“ReAct”与“Plan-and-Execute”是执行模式，“Memory”是组件。运行时 Harness 支撑执行；评测 Harness 检查系统效果。项目有 `harness` 目录，不代表接入了某个同名框架。

## Q11：动态 Few-Shot 是什么？几百条 bad case 怎么办？

> Few-Shot 就是给模型几个示例。动态指每次请求从示例库选相关样例，不是把几百条全部放进 Prompt。当前项目按字符相似度最多选两条。bad case 先核验原因和正确结果：理解或格式问题可整理成示例，业务知识缺失可更新知识库，执行错误则要修程序规则。原始错误记录不能直接当正确答案使用。

自动采集可以来自后台请求、工具结果和人工反馈，不一定要前台手动登记。当前项目只有预置案例与示例检索，还未接通线上采集和自动发布。也没有把示例检索验证成语义向量检索。

## Q12：Harness eval 做了吗？验证闭环算微调吗？

**记忆句：用例检查行为，改进修改系统，微调更新参数。**

> 做了离线评测，不只是手动跑通一次。它会加载固定用例、比较意图、槽位和工单结果，再汇总指标。目前 20 条场景全部通过，另外有 96 项单元和集成测试。更新规则、Prompt、知识库或示例库改变的是应用行为，回归验证检查改动效果，都没有更新模型参数，所以不属于微调。

若被问“怎么才能自我提升”：

> 要先执行系统并记录失败，核验正确结果，再按原因修改规则、知识、提示或示例，最后用未参与改进的测试集对照验证，审核后发布并支持回滚。不运行系统、没有反馈就不能证明提升。我的当前版本还没有完整自动闭环，已有的固定提升文案也不能作为实验结果。

## Q13：重复请求和并发库存怎么处理？

> 相同 request_id 重试时返回已有执行，避免重复派单。后台在快照上计算，提交前检查版本和共享库存等基线，发生竞争就有限重试，避免两个请求都按旧库存扣减。去重和状态目前都在内存中，不能承诺重启后恢复，也不能把单进程检查说成数据库或分布式事务。

## Q14：怎么证明这一版可用？

> 我先做固定离线回归，再专门控制竞争时序，让旧任务晚返回、两个会话竞争同一份库存，检查最终工单和库存。同时测 API 会话归属、重复请求、部门撤回确认，以及前端处理期间继续输入。当前是 96 项测试和 20 条离线场景通过。页面截图也复现了“水不用了”只取消矿泉水。这些证明当前模拟流程通过，不能代替真实模型、生产性能和酒店现场验收。
