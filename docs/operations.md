# 单酒店部署与值班手册

## 1. 部署范围

一个 API 进程负责全部业务写入，工作台通过 HTTP 调用 API。SQLite 为本机磁盘文件；只有 API 挂载数据卷，工作台既不挂库，也不接收模型密钥或管理员启动凭据。不得运行多个 API worker 指向同一数据库，第二个写入者会被拒绝。

部署以学校学术酒店为业务背景，初始化数据是示例客房，不能直接作为真实入住记录。上线前核对房间、当日业务日期、入住与退房日期、接待类别、库存和知识内容。配置 `AEGIS_PMS_FILE` / `AEGIS_KNOWLEDGE_FILE` 时输入文件不存在或字段非法会报错，不悄悄降级到示例。

初始化配置将 `AEGIS_BUSINESS_DATE` 设为当天日期，仅用于新数据库；重启恢复库内业务日期，由受控夜审推进。使用真实初始数据时，将批准的文件以只读方式挂载到 API，再将上述变量指向容器内路径；不要提交住客数据或打入公开镜像。

## 2. 初始化与启动

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe scripts/manage.py init
docker compose up -d --build
```

初始化以独占创建方式生成已忽略的 `deploy.env`，不会覆盖现有密钥，也不会把密钥打印到终端。请限制该文件访问权限（Windows 使用所在目录 ACL，Linux 默认文件权限 0600）。生成的个人岗位凭据在 `AEGIS_STAFF_KEYS_JSON` 中，通过受控方式交给相应工作人员；不要截图、发公开群或提交 Git。`AEGIS_STAFF_TOKEN` 仅用于管理员。

默认规则模式无模型消费；需要模型时只在 API 的部署配置中设置兼容地址、Key 和模型名，并把 `AEGIS_FORCE_RULES` 改为 `0`。前端页面不能修改全局 Key 或模型接口。

Compose 端口绑定回环地址：工作台 8501、API 8000。提供给酒店网络前，使用 HTTPS 反向代理，设置域名对应的允许来源、访问日志脱敏、请求体上限和网络访问策略。不要把开发模式 `AEGIS_AUTH_ENABLED=0` 暴露给住客网络。部署模式缺少鉴权、持久化或强密钥时启动失败。

## 3. 工作流程

1. 前台按现有入住流程核验身份与接待订单，在员工页登记本次入住。
2. 签发带有效期的住客凭证。凭证绑定 room_no、stay_id 和 session_id；通过受控渠道交给该住客，不放 URL。
3. 住客使用凭证打开服务页；可以补充、取消、改单和查服务进度。
4. 部门人员用自己的岗位凭据办理待办。配送中变更要确认实际撤回，无法撤回就如实拒绝；完成回执由员工操作。
5. 换客先结清旧工单，再明确确认更替入住。旧凭证被吊销，旧版本任务无法继续提交。
6. 前台审批延退、核验异常；经理查看审计。夜审提交当前业务日期，多次点击不连续推进。

延退审批携带当前申请编号，绑定本次入住；换客后不能批准旧申请。批准延退只确认退房时间，是否收费仍按已核验的接待订单与前台确认办理。部门岗位只获取履职所需的工单和房态，不能查询住客聊天档案。

当前会务模板不会编造会场、早餐时间或校园通行规则。将学校批准的政策整理进知识文件后再使用。会议室预订、校园许可、报销审批、收费和真实发票都需相应系统或人员办理。

学术模式不自动发放早餐券：是否含早按接待订单核验，本系统只保留申请记录，住客需联系前台，实际餐券由现有餐饮／前台流程办理，当前没有电子券发放和核销回执接口。

## 4. 状态与错误处理

| 现象 | 正确处理 |
| --- | --- |
| 请求仍在运行／超时 | 查询原 run_id；网络重试保持同一 request_id，不新建请求冒充重试 |
| 任务 `interrupted` | 重启导致本次计算无法确认完成；先查工单再重新提交，系统不会自动重放未知外部动作 |
| HTTP 401 / 403 | 前台核对凭证、有效期、本次入住和岗位；不要绕过权限或把管理员令牌交给住客 |
| HTTP 409 | 状态或版本已变化；刷新并核对当前记录，再决定操作 |
| HTTP 429 / 503 | 请求频率／执行容量／存储异常；停止重复点击，联系值班人员 |
| 回收物品待检 | 与可用库存分开；实际清洗、检验、盘点及重新入库由仓储流程办理，当前不自动转为可用 |
| 工单待人工核验 | 核对依据后记录已核验；该按钮不会自动绕过规则派单 |

`/health` 为轻量存活检查，`/ready` 检查执行器与已知存储故障，异常返回 503。值班人员还应监控磁盘容量、数据库备份和服务进程。当前没有真实酒店短信／电话告警渠道，紧急维修和人身安全事项应走酒店值班制度，不能只依赖聊天页面。

## 5. 备份与恢复

```powershell
python scripts/manage.py backup --database var/aegisstay.sqlite3 --output backups/aegisstay-2026-10-23.sqlite3
```

使用 SQLite backup API，一并读入 WAL 的已提交数据，再运行完整性检查。目标已存在则拒绝覆盖。容器内备份可执行：

```sh
docker compose exec api python scripts/manage.py backup --database /data/aegisstay.sqlite3 --output /data/backup-2026-10-23.sqlite3
```

备份包含会话和住客相关信息，应限制访问并按学校批准的保留周期管理。**恢复必须停 API**，保留当前库及 WAL/SHM 的完整副本后，用经过完整性校验的备份替换数据卷中的主库，移走原库对应的 WAL/SHM，再启动单个 API。不要在线覆盖数据库文件，也不要把旧 WAL 与恢复后的主库混用。每次恢复后使用测试凭证核对入住、库存、工单和历史消息，再开放访问。

## 6. 发布前检查

- 在离线环境运行全部测试和 Harness；确认不产生模型费用。
- 使用测试入住记录验证核验、签发、取消、派送、更换、完成、换客吊销和重启恢复。
- 核对已经批准的政策文件、真实 PMS 适配方式和外部回执；尚未对接时按本系统台账运行，不能声称外部系统已经完成同步。
- 备份部署配置与数据库，做一次离线恢复演练；确认升级回滚路径。
- 依据实际酒店规模测试容量，不将固定规则评测耗时当成生产承载能力。
