# 酒店服务目录、风险分级与入住数据规格

本轮按用户明确提出的单酒店落地背景补充现有 REQ-03/04/05/06/07/10/14。真实 WiFi/PMS 身份核验仍为方案，不新增身份证收集表单，也不宣称已接通学校系统。

## 本轮交付

1. 住客空状态展示湖面、建筑与倒影；开始对话后缩小湖景，输入区不被推到屏幕之外。保持一个输入框和内部历史滚动。
2. 常规客房物品使用统一目录：至少 24 个库存 SKU，名称、单位、分组、初始合成库存及借用品标识可对照；真实酒店须导入核准库存，不能用默认数字冒充实盘。
3. 对目录查询给出明确回复；按摩、泡澡等未核验项目不承诺存在，也不臆断学校没有。配置状态为 available / unavailable / unconfirmed，只有有来源的配置才能确认提供或不提供。
4. 未核验服务只记入当前入住的待核验需求计数，不自动变成酒店政策、Few-Shot 或新增服务；不保存身份证、不复制原始对话进案例库。
5. 处理口语附加成分，正常的“水，两瓶，给我再来一下，不用催”应申请 2 瓶水；混合未知物品仍不得静默删掉未知部分派单。目录咨询不能吞掉同轮送物、取消或报修；房卡与早餐券查询必须明确前台核验，不能当普通可用库存承诺。
6. 优先级分业务风险与时效：冒烟/漏电等明确危险信号为高；明确急需的正常送物为中；普通送物为低。情绪本身不生成工单，模型不能把硬风险降级；无法确认业务目标时澄清。分级不表示已经实现全局抢占队列或现场救援。
7. 在既有已配置供应商上运行有限合成联调，并记录实际模型返回、耗时、工单、数量、库存和取消结果；真实模型失败不得冒充规则通过。
8. 提供每次入住刷新、持久历史、WiFi 验证入口、数据库/Redis 及并发操作的清晰方案，区分已实现与拟议能力。

## 验收方法

- 自动：至少 12 个业务测试方法，覆盖常规 SKU、实时库存目录、服务三态/去重计数、口语水需求、风险不可降级、时效与否定、存量库新增 SKU 不凭空补货、8 位并发住客及入住换客隔离；所有旧测试保持。
- 界面：1280×720 与 390×844 复核空/活动两态，图片有建筑和倒影，图片没有拉伸，只有一个可见文本输入区，输入区 bottom 不大于视口高度；记录实际 DOM 和原图尺寸，截图不可重绘。
- 云端：至少包含普通送物、口语水需求、未知物品、全取消、范围外话题及风险升级；逐条保存模型是否实际返回。结论限定为该模型、该输入与该次运行，不外推准确率。
- 并发：使用 8 个独立住客身份请求同一共享库存，初值 24 条毛巾，总预留不超过 24、库存不为负、取消仅释放本人预留一次、其他入住不串读。受控 Event 竞态继续执行，不能靠手速证明异步安全。
- 发布：统一离线证据入口保存新的完整日志/JSON/来源哈希及 REQ 映射。云端联调独立保存，不混进固定 H01～H20 的离线分母。

## 方案选择

保留 Streamlit、单 API 写入者与 SQLite；本轮不引入 Redis、手机号/身份证数据库或模型微调。相较直接把请求全交给模型，目录与风险仍由程序核验，模型负责辅助理解和措辞。相较把所有东西放 Redis，关系库保存业务事实与历史更符合本项目恢复和审计要求。落地入口、跨入住生命周期和未来 Redis 的职责见配套数据方案。

配套说明：[入住数据与运营说明](../docs/stay_data_and_operations.md)。既有库新增物品初值为 **0**，由员工盘点入库；24 项目录的默认数字只用于新建合成环境。Docker 包必须实际包含目录与校园湖景资产，CI 构建后在容器中检查二者。
