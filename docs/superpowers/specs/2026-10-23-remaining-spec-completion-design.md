# 剩余规格补全设计

## 目的

把当前仓库中已经识别、但仍分散在主规格和实验方案里的三类内容整理成可以交给实施人员和验收人员直接执行的子规格：部署与运维边界、酒店现场验收、外部系统与模型扩展。文档补全不会把未联调的系统写成已实现，也不会改变当前运行时行为。

## 目标

- 为 REQ-14 提供配置、容器、持久化、备份、恢复、升级和回滚的责任边界。
- 为 FIELD-01～FIELD-06 固定前置条件、测试数据、操作顺序、量化门槛、证据文件、失败处置和清理方式。
- 为 FUT-01～FUT-06 固定外部契约、数据最小化、失败语义、上线门槛和回退要求。
- 让主规格、验收标准、实验方案、追溯矩阵和 README 可以互相找到这些子规格。

## 非目标

- 不实现 PMS、SSO、真实电子券、语义向量 RAG、云端模型或现场负载驱动。
- 不修改当前业务代码来制造“规格已完成”的假象。
- 不把 Docker 镜像构建成功解释成 Compose、卷权限、断电恢复或酒店现场已经验收。

## 方案选择

| 方案 | 取舍 |
| --- | --- |
| 一个大文档 | 入口少，但部署、现场和未来集成的责任边界容易混在一起，验收人员难以只执行自己负责的部分 |
| 保留现状，只继续扩写 experiments.md | 改动小，但主规格缺少可独立引用的设计契约，未来集成容易漏掉隐私、回滚和审批要求 |
| **拆为三个子规格并由主规格链接** | 文档边界与负责团队一致，现场目标仍集中在实验方案，适合当前单酒店落地阶段；采用此方案 |

## 交付文件

- `spec/design/deployment.md`：REQ-14 的当前实现、运行参数、备份恢复契约和上线前检查。
- `spec/field_validation.md`：FIELD-01～FIELD-06 的现场执行协议；所有当前状态仍为 `TARGET_NOT_RUN`。
- `spec/future_integrations.md`：FUT-01～FUT-06 的契约、治理、验收和回退门槛；所有当前状态仍为 `planned`。
- `docs/superpowers/plans/2026-10-23-remaining-spec-content.md`：文件所有权、审查顺序和可核对的完成标准。

## 设计不变量

1. `offline-code-baseline` 与酒店现场状态 `NOT_VERIFIED` 永远分开记录。
2. 现场实验必须使用批准的验收沙箱、合成入住和独立证据目录；不得使用真实住客或生产数据库。
3. 任何外部写操作都必须有幂等键、关联 ID、超时待确认语义、审计记录和可回退路径。
4. 学术待遇仍由人工核验；未来模型、知识库和 Few-Shot 更新不能绕过权限、库存、费用和审批校验。
5. 规格完成表示“方案、交付物和判定方式完整”，不表示现场测试已经通过。
