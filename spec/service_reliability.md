# 住客完整记录、送物取消与语言边界规格

本文件补充 REQ-03、REQ-05、REQ-06 与 REQ-10。当前验证范围仍为离线代码基线，真实供应商与酒店现场另行验收。

## SR-01 完整聊天归档

- 给模型使用的 `state.messages` 保持短窗口；不得再把该窗口当成住客完整聊天记录。内存运行时维护会话私有归档；持久化运行时使用 SQLite `aegis_messages`，不把全量聊天复制进模型快照。
- 接收成功的用户消息、正式提交的助手回复和员工通知按稳定 `message_id` 归档一次。被中断 worker 的临时回复不得进入归档；同一消息重复刷新不得产生新记录。
- 分页使用独占 `before` 游标，按 sequence 升序返回，每页限制 1～100 条。两种住客界面均从归档读取，每页展示 30 条，支持“加载更早记录”和“回到最新消息”；阅读历史时轮询不得重置当前页。
- 页状态绑定当前会话/入住/凭证及服务实例；切换住客或重置当前会话后不能沿用他人的历史页。页面仍保持单一输入框与固定高度消息面板。
- 内存模式保存当前本地会话内全部记录；进程重启后的恢复必须使用已有受鉴权 API 与 SQLite，不能用共享本地数据库或任意 URL 会话号冒充授权。修复前已从纯内存删去的正文无法追溯恢复。

验收：8 轮共 16 条均可查看；56 轮共 112 条能分页到首条且无遗漏、重复；模型窗口仍小于 16 条；两会话不串读、返回值修改不能改写归档。API 模式在重启和原有凭证校验下仍保留完整历史。

## SR-02 明确批量取消

- “全部都不要了”“全部取消”“所有送物都取消”“全都不要了”处理当前会话、当前入住和当前房间的送物，不再要求用户逐一说物品名。明确指定物品时范围限制到该物品。
- 运行中及排队中的匹配送物任务先失效，旧 worker 恢复后不得提交。待派送工单取消并仅释放一次预留库存；已派出/送达的工单仍须员工确认撤回或取回，不能直接退还可用库存。
- 排队任务的初始规则标签不能作为唯一取消依据。“两条毛巾”等已知物品目标应纳入范围；缺房号回复等执行后才明确为送物的任务，也必须在提交时按实际工单差量检查取消代际，防止取消前请求晚到提交。取消后的新需求仍可正常提交。
- 批量操作不改写各工单原 task_id；原任务与批量控制任务分别留痕。不能影响其他会话、其他入住、其他房间、工程或退房业务。
- 批量取消走确定性本地路径，不外呼模型；即使只有一个被阻塞的 worker、任务额度已满，或阻塞的是不相关工程任务，也须能执行取消。工程任务继续处理；供应商中的旧 HTTP 请求可能继续到超时，但过期送物结果不再写入。
- “不用了”仍在多单时澄清；“不要全部取消”“没说要全部取消”不得执行取消。取消退房等其他明确业务不能误取消送物。“全部取消，改成1条毛巾”“全部取消，再送1条毛巾”等复合写指令先澄清，不允许把改单动作带入批量取消循环。
- 只取消指定物品时，控制任务状态和 `cancelled_by_run` 只反映本次改变的工单。其他物品的待确认状态与此前取消的审计归属不得被覆盖。

验收：使用 Event 阻塞真实派送处理器，同时保留已提交工单与排队任务；取消应在释放 Event 前完成，原 3 条毛巾/吹风机请求不新增工单，已取消库存回到初值；其他住客订单保持不变。重复取消库存不增加；配送中的工单保留预留并显示待确认。

另分别阻塞工程处理器、规则未分类的房号补槽任务；取消必须在释放 Event 前完成，工程最终仍可建其应有工单，旧房号补槽不得晚建送物单。已结单吹风机申请撤回后仍为库存 5、待员工确认。指定毛巾的取消不继承水单的待确认状态，不改写此前浴巾取消的审计。

## SR-03 配送目录与复合请求

- 云模型的“送物”标签不能替代 SKU 校验。未知物品或目录中没有的物品不能以“综合物料”创建配送工单。
- “红牛和水都只要1瓶”“送红牛和1瓶矿泉水”“送可乐和毛巾”等复合请求中，不能静默删除未知部分后只派已知物品。必须先说明未核验物品，本次工单数与库存变化均为 0。
- “再加”“及”和“好吗”不是忽略未知部分的理由；“送1瓶矿泉水，再加1罐可乐”“送1瓶可乐及1条毛巾”“送矿泉水和红牛好吗”同样应阻止整次配送写入。
- 核验在业务入口、部门处理器及监督器分别执行，错误子 Agent 即使省略了未知部分，也不能提交。
- 已知物品库存不足仍按既有协调申请流程记录，预留为 0，不承诺送达、不允许员工确认派送。协调申请与已确认配送必须区分；本轮不新增不存在的商品库存。

验收：至少 7 个未知/复合样例，含模型错误分类和子 Agent 忽略未知物品反例，全部不得建配送单或扣库存。既有库存竞争测试仍通过。

## SR-04 情绪、时效与称呼

- “不需要很快但一定要急”是时效描述，不能因包含否定和“要”就变成取消或替换。已有多张工单时，“再来两瓶水”仍按新需求创建矿泉水 2 瓶。
- 着急、冷静、不要帮助等表达没有明确服务目标时，不得因模型意图或 sentiment 标签而创建送物、工程、续住、票券或经理工单。模型标签仅为提案，业务目标仍需输入依据。
- 单说“我很生气”“我非常愤怒，但不需要帮助”，以及“我不需要经理介入，只是很着急”，在规则与错误模型分类两条路径下都不得创建经理工单。明确的设施故障、投诉或危险信号仍按原业务处理，情绪可影响优先级，但不能凭空补出业务目标。
- 否认当前档案称呼后切换为中性称呼，并提示前台核验姓名；不得继续固定加“张先生”，也不得按住客自述改 CRM 姓名、房号、stay_id 或权限。称呼偏好随会话持久化。

验收：用户原句能新增 2 瓶矿泉水且保留旧工单；6 类错误模型分类对纯情绪输入均无业务副作用；另 3 句情绪/拒绝经理输入各覆盖规则与模型路径；否认姓名后的当前回复和下一轮回复均不加旧称呼，PMS 与授权保持原值。

## 手动核对顺序

在独立合成数据实例进入住客端，依次发送下列消息。受保护部署已通过凭证绑定房间，不需要在消息中添加房号；本地开发首次可用 `1128 送两条毛巾` 完成补槽。

| 输入 | 预期与状态核对 |
| --- | --- |
| 送两条毛巾 | 毛巾单 1 张，库存由 24 到 22 |
| 红牛和水都只要1瓶 | 提示红牛未核验，不新增单，水库存仍为 36 |
| 我不要帮助，我就只是很急 | 不新增工单，不取消现有毛巾 |
| 我很冷静，想再来两瓶水，不需要很快但一定要急 | 新增矿泉水 2 瓶，毛巾保留，水库存到 34 |
| 全部都不要了 | 这两张未派送单均取消，库存回到毛巾 24、水 36 |
| 只要吹风机3个 | 在上述初始库存条件下新建 3 个吹风机申请，可用库存由 6 到 3；其他申请已占用时以实际库存为准 |
| 我不是张先生 | 当前及下一轮使用中性称呼，入住权限不变 |

至少发送 16 轮后，在消息面板中点击“加载更早记录”，应能取回第一轮；“回到最新消息”返回新回复。页面截图仅证明展示；库存、取消竞态与重启恢复仍须自动测试和 API/数据库状态证据。
