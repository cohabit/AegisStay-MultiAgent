# AegisStay 多智能体系统验收标准与证据规范 (acceptance_criteria.md)

## 1. 量化验收指标 (Quantitative Metrics)

系统在接受交付或版本迭代时，必须严格满足以下量化指标。**所有数值均为硬性门槛，未达标直接判定为验收不通过**：

| 评估维度 | 指标项 (Metric) | 达标阈值 (Threshold) | 统计口径与说明 |
| :--- | :--- | :--- | :--- |
| **意图与复合解构** | 单意图分类准确率 (Single Intent Acc) | **100.0%** | 基于 `eval_dataset.json` 单轮与多轮用例 |
| | 复合意图双流解构率 (Compound Intent Coverage) | **≥ 95.0%** | 单次输入含 FAQ 与业务诉求时，两者兼顾的比例 |
| **槽位召回** | 房号抽取召回率 (Room No. Recall) | **≥ 98.0%** | 支持口语、房号前缀、后缀、独立数字提取 |
| | 延退时间解析准确率 (Time Slot Acc) | **≥ 98.0%** | 中文及数字时间折算下午时间（如“两点”→ 14:00） |
| **知识与回答边界** | 知识库检索准确率 (FAQ Precision) | **≥ 95.0%** | 针对早餐、Wi-Fi、发票等标准问答的准确命中 |
| | 范围外幻觉拒识率 (Rejection Rate) | **100.0%** | 闲聊、天气、作诗等非酒店服务提问不得瞎编，统一拒答 |
| **工单与派发** | 责任部门派发精准度 (Dept Precision) | **100.0%** | 送物→保洁、报修→工程、客诉→大堂经理，0 错派 |
| | 客诉高危升级触发率 (Red Alert Trigger) | **100.0%** | 含愤怒/差评词汇时，100% 触发红色高危并提升优先级 |
| **业务权益严谨性** | 黑金会员延退自动通过率 | **100.0%** | 仅且仅在黑金+在住+≤14:00+房态充裕时自动批准 |
| | 普通会员人工流转率 | **100.0%** | 普通会员或超限请求 100% 拦截并进入“需前台审核” |
| **性能与可靠性** | 规则离线模式单轮响应时间 (Latency) | **≤ 20.0 ms** | 纯本地规则引擎运行耗时 |
| | 系统异常崩溃率 (Crash Rate) | **0.0%** | 严禁未捕获异常导致前端 Streamlit 报错或中断 |

## 2. AI 测试通过证据标准 (Verifiable Test Proof Protocol)

任何负责修复、开发或优化本系统的 AI 助手（包括 Codex、Cursor、Claude、Antigravity 等），在汇报“任务完成”或“测试通过”时，**严禁使用“代码已修改成功”、“逻辑看起来没问题”等主观描述**，必须提供以下三项可机械验证的凭据（Evidence）：

### 2.1 凭据一：自动化单元测试执行日志 (Unit Test Proof)
必须在终端运行 `python -m unittest tests/test_app.py`，并回显如下完整的执行结果摘要：
```text
Ran 10 tests in 0.045s
OK
```
- **验证要点**：用例总数不得减少，结果必须为 `OK`，不可有 `FAILED` 或 `ERROR`。

### 2.2 凭据二：Harness 自动化质检量化报告 (Harness Benchmark Proof)
必须运行 `python -m harness.eval_runner`，并输出包含如下量化指标的 ASCII 表格与摘要：
```text
AegisStay Harness Evaluation
======================================================================================
Cases: 20 | Passed: 20 | Avg response: 2.15 ms
Intent Accuracy: 100.0%
Slot Filling Rate: 100.0%
Ticket Precision: 100.0% | Ticket Recall: 100.0%
--------------------------------------------------------------------------------------
ID    STATUS  INTENT   ROOM    DEPT     TICKET  NAME
H01   PASS    送物     1208    楼层保洁  True    单轮送毛巾
...
H20   PASS    其他     —       —        False   范围外天气
```
- **验证要点**：通过用例数必须等于用例总数（如 `20/20`），各项指标必须达到 100%。

### 2.3 凭据三：黑板状态与 Trace 轨迹断言凭据 (Blackboard Trace Proof)
对于特定边界场景（如复合意图、愤怒客诉、人工审批），AI 必须展示测试运行后 `HotelState` 的数据状态断言：
1. **复合意图测试**：输出的内容必须同时包含 FAQ 解答关键词与延退/工单业务结果；
2. **客诉测试**：断言 `state.tickets[0]["priority"] == "高"` 且 `state.tickets[0]["risk_level"] == "红色"`；
3. **退房审批测试**：断言在执行前台审核前后，`state.pms_rooms["808"]["checkout_time"]` 的变化符合预期。

## 3. 标准验收用例矩阵 (Verification Matrix)

在交付前，必须人工或脚本验证以下典型用例：

| 用例编号 | 测试类别 | 住客输入 Query | 预期 Agent 行为与输出断言 | 对应部门/状态 |
| :--- | :--- | :--- | :--- | :--- |
| **TC-01** | **复合意图** | `你们早餐几点结束？另外我是携程黑金，1128 能帮我两点退房吗？` | 1. 包含早餐时间（07:00–10:00）<br>2. 关联张先生黑金会员<br>3. 自动批准延退至 14:00 | PMS 退房时间更新为 14:00 |
| **TC-02** | **复合意图+缺槽** | `你们早餐几点结束？另外我是携程黑金，能帮我两点退房吗？`（不带房号） | 1. 必须回答早餐时间<br>2. 礼貌提示住客补充房号 | `state.pending` 记录延退意图 |
| **TC-03** | **多轮补槽** | 第1轮：`我想要两条毛巾`<br>第2轮：`1208` | 第1轮：询问房号，不派单<br>第2轮：创建送物工单 | 楼层保洁 / 优先级低 |
| **TC-04** | **工程与愤怒情绪** | `1208 房间空调坏了，很生气` | 1. 识别工程报修<br>2. 情绪为愤怒<br>3. 优先级由中自动升为**高** | 工程部 / 优先级高 |
| **TC-05** | **严重客诉预警** | `1128 投诉房间太吵，我非常生气，马上处理` | 1. 识别客诉紧急<br>2. 触发**红色高危预警**<br>3. 优先联系大堂经理 | 大堂经理 / 红色高危预警 |
| **TC-06** | **普通会员审批** | `808 能两点退房吗？` | 识别为李女士（普通会员），提示需前台人工审核 | `需前台审核` / PMS 不自动改 |
| **TC-07** | **人工闭环审批** | 前台点击“批准” 808 延退至 14:00 | 1. 请求状态变为 `已批准`<br>2. 808 退房时间更新为 14:00 | PMS 退房时间更新为 14:00 |
| **TC-08** | **范围外拒答** | `帮我写一首关于三亚的诗` | 礼貌拒绝，引导告知能提供的酒店服务范围 | 知识库 fallback / 不派单 |
