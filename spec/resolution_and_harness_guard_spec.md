# AegisStay 智能体工单消单闭环与 Harness 意图防幻觉 Spec

## 1. 背景与问题定位

在云端大模型质检（Harness）与真实住客交互过程中，发现以下两个关键体验与准确率缺陷：

### 问题 1：云端 Harness H13 评测失败（准确率 19/20，95.0%）
- **Case 现象**：
  - 测试用例：`H13`（名称：`退房 FAQ`），用户输入：`"退房时间是几点？"`
  - 预期意图：`"酒店咨询"`（`should_create_ticket: false`）
  - 实际结果：云端模型（如 Qwen2.5-7B）误判为 `"延迟退房"`，导致判定失败。
- **根本原因**：
  1. `ReceptionAgent.understand` 中的 LLM Prompt 未对“普通退房时间咨询”与“延迟退房申请”做边界约束，模型看到“退房”便容易泛化为“延迟退房”。
  2. 代码中的回退合并逻辑存在缺陷：
     ```python
     if result["intent"] in {"其他", "酒店咨询"} and cloud.get("intent") in SERVICE_INTENTS:
         result["intent"] = cloud["intent"]
     ```
     当规则引擎已经正确通过 FAQ 命中“酒店咨询”时，大模型幻觉输出的 `延迟退房`（属于 `SERVICE_INTENTS`）会无条件覆盖规则结果，即便住客未表达任何“延迟”、“推迟”或“延后”的诉求。

### 问题 2：住客确认“修好了”，系统误触报修导致重复建单与死循环
- **交互现象**（真实前端对话）：
  - 住客原先反馈：`"1102 卫生间花洒漏水"`，系统创建了报修工单 `HT-XXXX`（处理中）。
  - 维修师傅修好离开后，住客回复：`"可以了，他们来人修好了"`。
  - 系统响应：系统识别到“修”字或大模型误判为“工程报修”，不仅没结单，反而生成了一张全新的工单 `HT-YYYY`（工程报修 · 处理中），并回复：*“请先停止使用故障设备，工程部将按排查单逐项检查...”*。
- **根本原因**：
  - 缺乏**服务完结/消单确认（Resolution Feedback）**意图识别与状态机流转。
  - 针对带有“修好了/送到了/搞定了/收到了”的文本，模型误当成新报修，而工单去重逻辑仅比对 `item_detail == pending["detail"]`，由于文本不一致判定为新报修，导致严重业务逻辑漏洞。

## 2. 详细技术规范与改造方案

### 规范 1：精准意图守卫与 H13 防幻觉（LLM + 规则护栏）

1. **Prompt 边界明确化**：
   在 `ReceptionAgent.understand` 中调用大模型时，强化 System Prompt：
   > `提取酒店住客意图 JSON：intent(酒店咨询/送物/工程报修/客诉紧急/延迟退房/其他)、sentiment(正常/愤怒)。`
   > `特别注意：询问酒店设施政策、早餐时间、退房时间/退房规则（如'退房时间是几点'、'几点退房'）一律属于'酒店咨询'；只有明确提出推迟离店、晚走、延长退房时间（如'想延迟退房'、'延迟到两点'）才属于'延迟退房'。`

2. **代码级确定性护栏**：
   在 `ReceptionAgent.understand` 接收云端大模型结果时，针对 `延迟退房` 增加前置判定：
   - 若 `cloud.get("intent") == "延迟退房"`：
     仅当用户输入中存在明确延迟意图时（即满足下列条件之一）：
     1. 规则提取中已捕获到明确延迟时间（`result["requested_time"] is not None`）；
     2. 文本中包含明确的延迟动词/副词：`("延迟", "延时", "推迟", "晚点", "晚退", "多待")`。
   - 若用户仅询问 `"退房时间"`, `"几点退房"`, `"何时退房"`, `"退房规定"`, `"退房政策"`，即便云端模型返回 `延迟退房`，护栏必须强行纠偏，保持 `intent = "酒店咨询"` 并关联退房 FAQ，坚决拦截幻觉！

---

### 规范 2：服务完成闭环机制（消单/结单反馈状态流转）

1. **完成态关键词提取（`is_service_resolution`）**：
   定义消单确认词组：
   - 肯定完结词：`("修好了", "维修好了", "师傅修好了", "搞定了", "弄好了", "解决了", "已经好了", "送到了", "收到了", "拿到了", "处理好了", "弄妥了", "不用修了")`
   - 否定反转词排除：需排查 `("没修好", "还没修好", "没弄好", "还没送到", "没收到", "没搞定", "没解决")`，若包含否定词则属于追问催办，不可误消单。

2. **意图阻断**：
   当命中消单确认时：
   - `_rules_extract` 与 `ReceptionAgent.understand` 中，不得将该轮识别为 `工程报修` 或 `送物` 等需要创建新工单的 `SERVICE_INTENTS`。
   - 可将 `intent` 标记为 `"服务完结"` 或保持 `"其他"`，并将 `resolution_target` 标记为 `工程报修`（若含“修/维修/师傅/故障”）或 `送物`（若含“送/物/水/毛巾/拿到/收到”）。

3. **工单自动流转闭环（`handle_request` 处理逻辑）**：
   当检测到住客表达服务已完成时：
   - 检索当前房间 `state.room_no` 下处于 `status == "处理中"` 的工单列表：
     - 若指定了部门偏好（如提到“修好”），优先匹配 `category == "工程报修"` 的工单；
     - 若提到“送到/收到”，优先匹配 `category == "送物"` 的工单；
     - 若未明确提及部门但存在进行中的工单，直接匹配最近的一笔 `处理中` 工单。
   - **工单状态流转**：
     - 将目标工单的 `status` 修改为 `"已结单"`；
     - 记录 `completed_at = datetime.now().isoformat(timespec="seconds")`；
     - 记录责任 Agent trace：
       `{"agent": ticket.get("agent", "EngineeringAgent"), "event": "服务完结闭环", "detail": f"住客确认完成，工单 {ticket['ticket_id']} ({ticket['category']}) 已流转为已结单"}`；
   - **智能体礼貌致谢回复**：
     - 若成功结单：
       `"{住客尊称}，收到您的反馈，很高兴问题已为您妥善解决！对应服务单（{category}）已为您办结。祝您入住愉快，如还有其他需要请随时告诉我们。"`
     - 若当前房间并无处于处理中的工单：
       `"{住客尊称}，收到您的反馈，很高兴服务让您满意！祝您入住愉快，随时为您效劳。"`
   - **状态清理**：清空待办 `state.pending = None`，**绝不创建任何新工单**。

## 3. 验收标准与测试矩阵

1. **Harness 评测验证**：
   - 运行 `python -m harness.eval_runner`（无论离线还是云端 API）：
   - `H13`（`"退房时间是几点？"`）必须 100% 判定为 `酒店咨询`，`status_ok == True`，20/20 全部 PASS。
2. **消单闭环单测**：
   - **工程完结测试**：
     - Round 1: `1102 卫生间花洒漏水` -> 创建工程工单（处理中）。
     - Round 2: `可以了，他们来人修好了` -> 工单状态变为 `已结单`，工单总数保持为 1，不生成第 2 张工单，回复中确认已办结。
   - **送物完结测试**：
     - Round 1: `1208 送两瓶水` -> 创建送物工单（处理中）。
     - Round 2: `水收到了，谢谢` -> 工单状态变为 `已结单`，工单总数保持为 1。
   - **否定未完结保护**：
     - Round 1: `1102 卫生间花洒漏水` -> 工单处理中。
     - Round 2: `师傅还没修好呢` -> 工单状态依然为 `处理中`，不得误结单。
