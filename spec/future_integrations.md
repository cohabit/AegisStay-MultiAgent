# 外部系统与模型扩展子规格

本文件是 FUT-01～FUT-06 的唯一权威定义，供实施、评审和现场验收使用。它把外部系统、知识检索和样例治理写成可执行的契约；它不表示任何外部系统已经接通。

## 状态、范围与共同不变量

| 项目 | 当前状态 | 现场/发布含义 |
| --- | --- | --- |
| FUT-01 真实 PMS 双向适配 | `planned` | `FIELD-05=TARGET_NOT_RUN`；当前 `shared_pms` 是合成/本地台账，不是外部 PMS |
| FUT-02 学校 SSO | `planned` | `FIELD-05=TARGET_NOT_RUN`；当前是 `auth.py` 的本地岗位令牌映射 |
| FUT-03 电子券签发、核销、撤回、对账 | `planned` | `FIELD-04/05=TARGET_NOT_RUN`；当前 academic 只记录“需前台核验”，没有真实签发接口 |
| FUT-04 学校批准知识与语义检索 | `planned` | `FIELD-04/06=TARGET_NOT_RUN`；当前没有向量数据库或语义 RAG |
| FUT-05 容量、可观测性、容灾与恢复 | `planned` | `FIELD-01/02/03=TARGET_NOT_RUN`；当前参数是实现默认值，不是生产容量承诺 |
| FUT-06 失败样例治理与独立对照 | `planned` | `FIELD-06=TARGET_NOT_RUN`；当前没有线上自动采集或自动发布闭环 |

所有集成必须遵守这些不变量：

1. `offline-code-baseline`、`field_readiness=NOT_VERIFIED` 和未来项目的 `planned` 状态分开记录。静态配置、本地模拟或历史日志不能把状态提升为已联调、`PASS` 或生产可用。
2. 外部写操作使用统一关联信封：`integration`、`operation`、`request_id`、`idempotency_key`、`correlation_id`、`entity_id`、`entity_version`、`sent_at`、`deadline`、`actor` 和 `data_classification`。外部响应必须带 `provider_request_id`、`provider_event_id`、`provider_status`、`provider_version`、`received_at` 和 `outcome`。
3. 成功只在本地提交和外部回执均达到契约状态时返回。超时、断线、未知回执和版本冲突均显示“待确认/需人工核验”，不能写成成功；重试不得产生第二个外部效果。
4. 外部适配器位于 API/runtime 的边界。`server.py` 或独立适配器负责网络、鉴权、重试和回执；`agent_runtime.py` 的 `SessionManager` 负责本地 `request_id`、`stay_id`、会话和原子检查点；`hotel_core.py` 的处理器只产生经过 `validate_department_ticket` 等护栏的提案。住客、模型和部门处理器不能直接持有外部凭据或提交外部写操作。
5. 只传必要字段。日志、Trace、指标和证据使用 `room_no`/`stay_id`/`session_id` 的不可逆哈希或内部 ID；禁止记录访问令牌、SSO 断言、券码、完整姓名、原始聊天逐字稿和完整外部报文。发送真实资料前须有学校/酒店的数据处理批准。
6. 每项实施都要提供沙箱契约测试、同一关联 ID 的双侧前后状态、脱敏报文、事件顺序、HTTP/业务状态、审计记录、失败样本和回滚记录。字段字典、时钟、时区、错误码和保留期限在接入前版本化。

## FUT-01：PMS 双向适配、回执与补偿

**状态：** `planned`；关联 `FIELD-05=TARGET_NOT_RUN`。

**目的和非目标。** 将外部 PMS 的入住、换客、房态、退房时间和订单审批状态同步到 `shared_pms`，并在需要时把经过前台审批的入住/延退/退房变更写回 PMS。适配器必须保持本地 `stay_id`、房号和工单归属的一致性。它不负责替学校解释未知政策，不自动批准 academic 延退，不把 `data/pms_rooms_240.json` 或 `AEGIS_PMS_FILE` 伪装成双向集成，也不改变单 API 写入者和 SQLite 原子检查点的约束。

**概念契约和数据。** 适配器接收或发出下列版本化资源（字段为概念字段，最终字段字典由 PMS 沙箱批准）：

- `StaySnapshot`：`provider_stay_id`、`reservation_id`、`room_no`、`stay_id`、`occupancy_state`、`checkin_at`、`checkout_at`、`checkout_time`、`profile_scope`、`source_version`、`effective_at`、`event_id`。
- `PmsMutation`：`operation`（`check_in`/`room_move`/`late_checkout`/`checkout`/`cancel`）、`stay_id`、经前台核验的 `expected_version`、变更字段、`approval_id`、`idempotency_key` 和 `correlation_id`。
- `PmsReceipt`：`provider_request_id`、`provider_event_id`、`accepted_version`、`status`（`accepted`/`rejected`/`pending`/`unknown`）、错误码、可重试标记、`received_at`。
- `PmsReconciliation`：本地版本、外部版本、差异字段、首次发现时间、处理人、处置（重拉、人工确认、撤销本地待提交）。

入站事件按 `provider_event_id` 去重，并按同一 `provider_stay_id` 的 `source_version` 单调应用；旧事件只能被记录为过期，不能覆盖新房态。出站事件必须先有本地提交记录，外部确认后才能将业务状态推进为已确认。

**身份、隐私和网络边界。** 使用专用服务账号和 mTLS 或 OAuth2 client credentials；权限仅限指定酒店、房态读取和获批变更。住客姓名、联系方式和备注不进入运行时或日志，除非字段字典和批准清单明确需要；测试只用合成入住。外部地址、证书和 token 只来自部署密钥管理，不写入 Git、测试输出或 `manifest.json`。

**幂等、顺序和时限。** `idempotency_key = integration + operation + stay_id + request_id`，同键不同载荷必须拒绝并报警。连接超时 2 秒、读取超时 10 秒、单次总预算 15 秒；最多两次重试（1 秒、3 秒），只对明确可重试的网络/5xx 重试。超出预算进入 `pending_confirmation`，后台重拉或人工确认不得自行重放未知写入。每个 stay 的事件队列保持版本顺序；跨 stay 可以并行。定期对账默认每 5 分钟一次，发现版本差异立即阻止该 stay 的自动写回。

**失败和人工回退。** 外部 4xx、版本冲突或字段缺失进入 `needs_review`，保留本地申请，不扣库存、不改变房态；5xx、超时和断线进入待确认并显示关联 ID。前台可在受保护操作台按 `provider_request_id` 查询或电话核对，人工确认后再补写本地记录。PMS 不可用时停用外部写回，继续提供已缓存且带 `source_version` 的本地服务，入住、换客和延退回到人工台账；服务恢复后先对账再解除阻断。

**审计和保留。** 结构化审计至少包含 actor、operation、entity、旧/新版本、关联 ID、外部状态、重试次数、人工处置和时间。脱敏报文保留 30 天用于排错；状态、哈希和审批审计保留 180 天；安全事件和对账差异保留 1 年，具体期限须由学校批准。到期删除报文内容而保留不可逆统计，删除动作自身要有审计记录。

**分阶段交付、依赖和验收。** 阶段 0 冻结字段字典、时区、错误码和沙箱账号；阶段 1 只读同步并 shadow 比对；阶段 2 在沙箱启用审批后的单笔写回；阶段 3 进行可控乱序/故障演练和一间合成房间的 canary；阶段 4 才能提出生产开关申请。依赖 `FIELD-04` 的政策核验、`FIELD-05` 的 PMS 契约和 `FUT-02`（若身份由 SSO 提供）。验收至少覆盖 FIELD-05 的 20 种 PMS 场景：有效/失效入住、换客、重放、延迟/重复/乱序回执、4xx/5xx/超时、网络恢复和缺字段；每场景双侧状态与关联 ID 100% 可追溯。零容忍：跨房或跨住客写入 0 次、未知结果报成功 0 次、同一键重复外部效果 0 次、换客后旧 stay 写入 0 次、审计缺失 0 次。回执乱序和故障演练各重复 10 轮，全部通过后才可启用写回。

**回滚。** 保留最后一个已批准的适配器配置和字段版本；发现任一安全或一致性错误立即关闭外部写开关、保留本地待确认记录、切回人工 PMS 台账。不得删除外部订单或用旧快照覆盖新房态；恢复前先暂停写回、重拉快照、人工处理差异并重新运行契约门槛。

## FUT-02：学校 SSO、组织账号和生命周期

**状态：** `planned`；关联 `FIELD-05=TARGET_NOT_RUN`。

**目的和非目标。** 用学校批准的 OIDC（首选）或 SAML 身份源替代部署中的手工岗位令牌，并把组织账号、岗位、退出和撤销事件安全映射到 `auth.py` 的 grant/session 检查。SSO 只证明身份和组织关系，不自动授予房间、stay、审批或跨部门权限；不把来宾自称学校成员、邮箱域名或模型判断当作认证结果。

**概念契约和数据。** 认证适配器保存最小 `IdentityAssertion`：`issuer`、`subject`、`audience`、`nonce`、`auth_time`、`expires_at`、`acr`、`groups`（仅批准组）、`directory_version` 和 `provider_event_id`；内部 `Principal` 为 `principal_id`、映射岗位、允许站点/部门、状态、`last_verified_at` 和 `grant_id`。生命周期事件为 `provision`、`role_change`、`suspend`、`revoke`、`delete`，带 `sequence`、`effective_at` 和原因。`room_no`、`stay_id` 仍由入住凭证和运行时 grant 绑定，不能从 SSO claim 推导。

**身份、隐私和网络边界。** 使用授权码 + PKCE、严格 issuer/audience/签名/nonce 校验；服务端 token endpoint 使用 mTLS 或私网连接。只保存不可逆 subject 映射、岗位和撤销状态，不保存 access/refresh token、原始断言或不必要的姓名/邮箱。前台/经理岗位映射须由学校目录管理员和酒店负责人双人批准；客人身份仍由入住台账和 `grant_id` 绑定。

**幂等、顺序和时限。** 每个登录 callback 的 `nonce` 只能消费一次，`state` 绑定浏览器会话；生命周期以 `provider_event_id + sequence` 去重并按 subject 单调应用。发现旧 sequence 时只记审计，不恢复旧岗位。发现时钟偏差超过 60 秒、token endpoint 连接 2 秒或总时限 10 秒、目录查询总时限 5 秒即失败；不得用缓存过期身份完成高风险操作。撤销事件达到本地后立即使相关 grant/session 和在途 worker 失效。

**失败和人工回退。** 错签名、错误受众、过期、nonce 重用、岗位不在映射或目录不可用均拒绝登录并记审计；不能以 200 或旧页面状态掩盖失败。学校 SSO 不可用时，已在岗的低风险查看可按短 TTL 缓存继续；新登录、审批、入住、跨部门操作暂停。经双人审批的 break-glass 前台账号只能用于短时恢复，必须绑定工单、15 分钟过期并在 SSO 恢复后立即撤销；住客没有离线绕过路径。

**审计和保留。** 记录 issuer/subject 哈希、岗位映射版本、成功/失败原因、grant/session、sequence、撤销和人工处置；不记录断言全文或 token。认证安全事件保留 1 年，最小登录审计保留 180 天，学校删除/撤销请求在 24 小时内传播并保留处置证据。访问审计只允许 manager/admin，部门视图不含账号目录。

**分阶段交付、依赖和验收。** 阶段 0 取得学校 IdP 元数据、组字典、撤销 SLA 和隐私批准；阶段 1 在沙箱只验证登录和 claim 映射；阶段 2 接入岗位和撤销但保留本地 token 回退；阶段 3 做 canary；阶段 4 才允许默认 SSO。依赖 `FIELD-05`、`FUT-01`（PMS 身份关联可选）和现有 `auth.py`/`server.py` 授权测试。至少覆盖 20 种身份场景：登录、错误受众/签名/过期、越权、撤销、换人、会话固定、退出、重放、乱序生命周期和 IdP 超时。零容忍：错误或过期断言登录 0 次、越权写 0 次、撤销后旧 grant 成功 0 次、旧岗位在新 sequence 后生效 0 次、令牌出现在日志 0 次；全部测试和撤销传播 100% 可追溯。

**回滚。** 由 feature flag 关闭 SSO 登录入口并恢复现有本地岗位令牌映射；先撤销 SSO 会话和缓存 grant，再保留审计与人工处置记录。不能删除学校目录事件或把已撤销身份重新激活；重新启用前须清理缓存并重跑全部身份场景。

## FUT-03：电子券签发、核销、撤回与订单对账

**状态：** `planned`；关联 `FIELD-04=TARGET_NOT_RUN`（真实发行验收还依赖 `FIELD-05`）。

**目的和非目标。** 在学校批准的待遇、接待订单和前台核验完成后，连接真实券服务完成签发、核销、撤回和对账。该集成不能自行判断“含早”、教师/会员自述或未知政策，也不能让保洁直接发券、把普通库存物品转换成券或在核验前预留真实券。当前 academic 规则必须继续产出“需前台核验”，而不是“已发放”。

**概念契约和数据。** 建议资源为：

- `VoucherEntitlement`：`entitlement_id`、`stay_id`、`reservation_id`、政策版本/`approval_id`、券种、数量、有效起止、发放主体、状态和 `correlation_id`。
- `VoucherGrant`：本地 `voucher_id`、外部 `provider_voucher_id`、数量、币种/面值（如适用）、`idempotency_key`、`status`（`requested`/`issued`/`redeemed`/`reversed`/`unknown`/`void`）。
- `Redemption` 与 `Reversal`：券 ID、订单/消费点、数量、时间、外部回执、原因、审批人和原事件版本；撤回只能引用已签发且未核销部分。
- `VoucherReconciliation`：本地台账、接待订单、外部券服务三方计数、差异、最后对账时间和处置。

**身份、隐私和网络边界。** 使用最小权限服务账号和 mTLS/OAuth；券码只在受保护前台/供应商通道短暂显示，日志只记哈希。每一笔 entitlement 必须绑定当前 `stay_id`、入住凭证和获批政策版本；住客、模型和 housekeeping API 没有发行权限。对账只同步必要订单标识和数量，不上传聊天逐字稿。

**幂等、顺序和时限。** 签发键为 `entitlement_id + voucher_type + version`，核销/撤回键为外部事件 ID；同键不同载荷 409。签发连接 2 秒、读取 8 秒、总时限 12 秒；最多一次明确可重试的重放，超过预算进入 `unknown` 并人工/供应商查询。状态只能按 `requested → issued → redeemed → reversed/void` 前进，重复回执无副作用，撤回不能越过已核销数量。订单和券账本每 15 分钟对账一次，差异期间阻止新的同 entitlement 签发。

**失败和人工回退。** 资格或政策缺失时保留本地核验记录，不调用供应商；供应商 4xx/拒绝进入人工核验；5xx/超时只显示待确认，绝不再次盲签发。供应商不可用时前台可按批准单人工记录，housekeeping 继续拒绝券类 dispatch；恢复后先查询外部状态再补台账。核销失败不得自动把券标为已用，撤回失败不得删除原记录。

**审计和保留。** 记录政策 hash、审批人、stay/session 哈希、供应商事件、状态迁移、数量前后、人工处置和三方对账差异；不记录完整券码。脱敏供应商报文保留 30 天；券和订单财务审计保留 2 年或学校/供应商较长要求；访问/撤回操作保留 1 年。删除或更正需保留原审计链，不允许直接覆盖历史状态。

**分阶段交付、依赖和验收。** 阶段 0 完成学校待遇矩阵和供应商沙箱；阶段 1 只读查询/对账；阶段 2 沙箱签发、核销、撤回；阶段 3 一项合成接待订单 canary；阶段 4 才申请生产写权限。依赖 `FIELD-04` 政策批准、`FIELD-05` 身份/PMS 关联、现有 `hotel_core.py` 礼宾核验边界。至少 30 个生命周期契约场景（含重放、超时、乱序、部分撤回、核销后撤回、订单换客）并覆盖 FIELD-04 的 20 个权益变体。零容忍：未审核签发 0 次、保洁直发 0 次、错误 stay/房号 0 次、重复外部效果 0 次、未知状态报成功 0 次、三方对账未解释差异 0 条；发行、核销、撤回和对账状态 100% 可追溯。

**回滚。** 关闭发行/核销/撤回外呼，只保留“需前台核验”本地台账；已得到供应商确认的券不能本地伪撤回，需按人工供应商流程处理并保留 provider ID。回滚后先完成三方对账、封存未决 entitlement，再允许重新启用。

## FUT-04：学校批准知识、语义检索与审核

**状态：** `planned`；关联 `FIELD-04=TARGET_NOT_RUN`、`FIELD-06=TARGET_NOT_RUN`。

**目的和非目标。** 把学校批准的早餐、会务、通行、报销、延退和待遇政策整理成带有效期、范围和出处的知识集合，并可选引入语义检索来辅助 FAQ/核验路由。语义检索只能提供带出处的候选证据，不能替代前台审批、房间/入住授权、库存或提案校验；过期、冲突或无出处内容必须转人工。

**当前实现的明确边界。** 现在的 `data/academic_hotel_knowledge.json` 和 `data/hotel_knowledge.json` 是本地模板，代码使用关键词、短语和字符序列相似度；没有向量数据库、embedding 索引或语义 RAG。`harness/self_evolution.py` 的 DynamicExemplarCurator 只检索难例/Few-Shot 示例，不能称作语义检索。新增或替换 Few-Shot 示例只是运行时提示/示例数据更新，**不会微调或更新模型参数**；没有独立前后对照就不得声称提升。

**概念契约和数据。** `ApprovedKnowledgeDocument` 包含 `document_id`、标题、正文/分块哈希、来源机构、政策 owner、`site_scope`、适用角色、`effective_from`、`effective_until`、版本、批准人/日期、撤销原因和分类。`RetrievalRecord` 包含查询哈希、索引版本、候选 `chunk_id`、分数、出处、有效期检查、过滤原因和最终人工/规则决定；模型输入只接收已批准分块，不接收原始住客逐字稿。索引发布是原子版本切换，旧版本可回退。

**身份、隐私和网络边界。** 只有 policy owner、manager 和受委托审核人能写入或批准文档；guest/department 只能读其范围内的最终答案。向量和正文按站点/角色隔离、加密存储，检索日志不含原始查询。若调用云模型，必须有学校批准的数据处理、区域和留存约束；默认规则路径在模型不可用时继续工作。

**幂等、顺序和时限。** 以 `document_id + version + content_hash` 去重；同文档版本只能有一个生效索引。撤销或过期事件按版本单调应用，旧索引不得重新激活。在线检索预算为 2 秒，目标 P95 500 ms；索引发布采用双版本校验，失败保留旧版本。超时、空候选、冲突或出处失效均回退到当前关键词/字符相似度路径，再无法确定时返回需核验。

**失败和人工回退。** 索引损坏、向量服务不可用、模型超时/坏格式/虚假房号或安全降级提案均不得直接写业务；记录 trace 并走规则护栏。政策 owner 可撤销一版文档，前台在操作台确认后才能恢复旧批准版。任何未带出处的语义答案都视为失败，不得用相似文本补齐未知会议时间、地点或免费权益。

**审计和保留。** 保留文档版本、审批链、content hash、索引构建、检索候选/过滤原因、最终回复和回退原因；不保留住客原始逐字稿。批准文档和撤销记录至少 2 年；检索决策元数据 180 天；临时 embedding/构建缓存 30 天。学校删除请求、过期政策和数据集污染事件必须可定位并有删除/重建审计。

**分阶段交付、依赖和验收。** 阶段 0 建立政策清单、owner、版本和出处；阶段 1 只做离线索引与 shadow 检索；阶段 2 以 FIELD-04 的人工标注样本做规则/语义并行；阶段 3 小流量启用带引用答案；阶段 4 才评估云模型或更大语义索引。依赖 `FIELD-04` 的政策审批、`FIELD-06` 的独立评测和现有 FAQ/提案边界。验收至少包含 FIELD-04 的 40 条政策查询和 20 条权益变体，以及 FIELD-06 的独立 200 条集（至少 40 条身份/权益/取消/冲突安全边界）；已批准且未过期答案出处覆盖 100%，过期/未知/冲突转核验 100%，越权/未审权益/重复扣库 0 次，检索 P95≤500 ms，模型/检索失败回退 100%。任何数据集污染、无审批文档生效或安全反例即阻断。

**回滚。** 原子地切回上一批准索引/知识版本，或完全关闭语义/云路径，恢复当前内置关键词、短语和字符相似度路径。回滚不删除审计；先隔离问题文档、冻结新发布，再重新构建并通过独立集后才可恢复。

## FUT-05：现场容量、可观测性、灾备与恢复

**状态：** `planned`；关联 `FIELD-01/02/03=TARGET_NOT_RUN`。

**目的和非目标。** 在受保护部署中建立请求、任务、库存、存储、备份、告警和恢复证据，验证单 API 写入者在目标负载下的延迟与一致性，并给出可承诺的 RPO/RTO。它不引入多 worker 写库、不用 `tests/stress_test.py` 的无鉴权 reset 入口冒充现场压测，也不把默认 `max_workers=8`、`max_pending=128` 当作容量结论。

**概念契约和数据。** 每个请求/任务记录 `request_id`、`run_id`、`session_hash`、route、status、run_status、queue_ms、compute_ms、commit_ms、total_ms、revision、error_class 和时间；指标按站点、接口和状态聚合。告警事件含 `alert_id`、规则版本、阈值、首次/最近时间、去重键、值、确认人和处置。备份清单含数据库版本、WAL/SHM 状态、integrity_check、源/目标哈希、生成时间、RPO；恢复记录含故障点、恢复起止、RTO、丢失/重放 run 和校验结果。所有可观测数据去标识化。

**身份、隐私和网络边界。** 指标写入使用只写遥测账号，管理和恢复使用独立 admin/manager grant；告警通道不含房客姓名、聊天正文、token 或券码。备份按学校批准的加密和最小访问策略存储，恢复演练只用合成入住和专用验收卷；导出日志须脱敏后才能离开现场。

**幂等、顺序和时限。** 告警去重键为 `rule + site + entity + time_bucket`，相同故障不重复开单；备份序号单调，目标间隔≤15 分钟。`/ready` 在写库不可用、恢复未完成或双 writer 检测时返回非就绪并停止新写入；恢复后先完整性检查再开放。保留 FIELD-02 的每凭证 20 次/分钟限制，过载应明确 429/503，不混入正常成功率。

**失败和人工回退。** 磁盘满、只读、锁冲突、数据库损坏或外部遥测不可用时，写请求返回 503/待确认并保持业务内存与库存不变；值班前台切到人工台账。恢复流程必须停掉所有 writer，保留现库及 WAL/SHM，使用完整性通过且不覆盖目标的副本启动单实例；恢复期间不得用旧备份覆盖较新日期或凭证。

**审计和保留。** 原始逐请求样本至少保存至 FIELD-02/03 复核完成，默认脱敏 30 天；聚合指标、告警和备份目录保留 180 天；恢复与安全审计保留 1 年。每次查看、导出、恢复和删除都记录 actor、范围和结果；生产日志不得以“调试”理由绕过访问控制。

**分阶段交付、依赖和验收。** 阶段 0 完成 FIELD-01 的容器、卷、单 writer 和 `/ready`；阶段 1 建立指标/告警和鉴权负载驱动；阶段 2 完成 FIELD-02 负载与延迟；阶段 3 完成 FIELD-03 故障钩子、备份和恢复；阶段 4 才能提交容量或恢复 SLA。验收必须逐项执行 FIELD-01/02/03：20 个独立会话、20 个最大并发、30 分钟、至少 6000 个业务请求；正常请求成功/预期 run_status≥99.5%、未预期 5xx/超时≤0.5%、P95≤1500 ms、P99≤3000 ms；跨会话泄漏、负库存、重复执行、丢失已确认提交均为 0。FIELD-03 每种故障标记重复 10 轮，RTO≤120 秒，持续备份 RPO≤15 分钟，恢复演练 RTO≤15 分钟；已提交崩溃流程 RPO=0。任一硬门槛失败都不能承诺容量或恢复 SLA。

**回滚。** 先停负载和新写入，保留原卷、WAL/SHM、备份和指标，再按运维手册恢复单实例。性能不达时降低承诺并修复瓶颈，不能提高阈值掩盖失败；只读/磁盘满解除后必须重新做完整性检查和焦点幂等，不能只刷新页面。

## FUT-06：线上失败样例授权、脱敏、版本化与独立对照

**状态：** `planned`；关联 `FIELD-06=TARGET_NOT_RUN`。

**目的和非目标。** 将经过授权的失败/歧义样例转化为可审计、可删除、可回退的评测、提示或知识候选，并以独立冻结集做前后配对对照。该项目不自动把住客逐字稿写入 Few-Shot，不自动发布提示，不把示例检索称作模型训练，也不微调模型参数；线上样例不能绕过政策、身份、库存和提案护栏。

**概念契约和数据。** `FailureSample` 包含 `sample_id`、来源事件哈希、时间桶、脱敏版本、合法依据/同意状态、失败类别、期望行为、实际解析/业务状态、风险标签、数据集分区、创建者和删除期限；原始文本只在隔离队列短暂存在。`ReviewDecision` 包含 reviewer、双人复核、批准/拒绝原因、政策版本、隐私检查和 `decision_at`。`EvolutionRelease` 包含基线/候选提示、知识/Few-Shot 哈希、模型版本、温度、seed、预算、独立集哈希、指标和回退指针。样例必须从训练/提示候选集与独立测试集去重，禁止同源泄漏。

**身份、隐私和网络边界。** 只有授权的数据 steward、policy owner 和评测负责人能查看隔离原文或批准脱敏样例；实施人员只读去标识后的候选。自动脱敏必须覆盖姓名、房号、电话、邮箱、凭证、token、券码和自由文本中的直接标识；无法确认脱敏即拒绝入库。保留合法依据、删除请求和学校/酒店批准，不向云模型发送未经批准的真实资料。

**幂等、顺序和时限。** 以 `source_event_hash + redaction_version` 去重，重复事件不生成第二样例；审核状态按 `quarantined → redacted → reviewed → approved/rejected → released/retired` 单向推进。每个样例 24 小时内进入人工队列，超时自动隔离而不是自动发布；候选模型/检索调用单次推理目标超时为 10 秒、端到端请求预算为 15 秒，超时立即回到规则路径；release 使用单调版本和原子指针，任何候选只能由人工批准切换。在线采集故障不应阻塞住客请求，采集失败只记录计数并走现有规则路径。

**失败和人工回退。** 脱敏失败、来源未授权、测试集污染、审核分歧、模型超时、坏格式、虚假房号或风险降级提案均丢弃/隔离候选并保留原因；当前已发布版本继续服务。人工可从样例库撤销一版并恢复上一 `EvolutionRelease`；模型或语义路径不可用时，回到 `AEGIS_FORCE_RULES`/现有关键词与字符相似度路径，不能以低质量示例补发权益。

**审计和保留。** 原始隔离材料默认不超过 7 天且仅限 steward；脱敏样例和审核记录保留 180 天，发布哈希、指标和撤销记录保留 2 年，删除请求在 24 小时内完成并保留不可逆处置证明。记录每次查看、导出、脱敏规则版本、审核人、release、回滚和独立集哈希；公开证据只含聚合指标和脱敏 ID。

**分阶段交付、依赖和验收。** 阶段 0 获得数据治理、删除和同意规则；阶段 1 只做隔离采集与脱敏拒绝；阶段 2 由双人审核生成候选并固定独立集；阶段 3 影子运行并比较无示例/有示例；阶段 4 小流量 canary 后才允许发布。依赖 `FIELD-06`、`FUT-04` 的知识版本、`FUT-05` 的可观测性和当前 `harness/self_evolution.py` 的检索边界。验收至少冻结 200 条独立样本，其中至少 40 条为权益/身份/取消/冲突安全边界；无示例与有示例各运行每条至少 3 次，固定模型/提示/知识哈希、seed、温度和预算，报告配对结果及 95% 置信区间。零容忍：未经审批样例发布 0、独立集泄漏/重复 0、越权/未审权益/重复扣库 0、令牌或直接身份泄漏 0、模型失败时未回退 0；失败回退率 100%，一键恢复上一版本并在 5 分钟内生效。若区间不支持正向提升，结论必须写“未证明提升”，不能预写百分比。

**回滚。** release 指针原子切回上一批准版本，停止新样例发布并隔离问题样例；若云模型或语义索引异常，关闭外呼，恢复现有离线规则和字符相似度 Few-Shot。回滚后重新核对独立集哈希、权限、审计和安全反例，未经新一轮门槛不得恢复。

## 依赖关系与状态判定

推荐顺序是 `FIELD-04 → FIELD-05 → FUT-01/FUT-02 → FUT-03`，并行准备 `FUT-05` 的部署证据；`FUT-04` 和 `FUT-06` 只能在 `FIELD-04` 政策批准、`FIELD-06` 独立评测和回滚机制就绪后进入 canary。任何一个项目的契约测试、脱敏审计、故障回退或零容忍门槛未满足，状态继续保持 `planned`。只有集成人员在新证据目录中记录沙箱/现场实际运行、版本、原始报文、审计和回滚结果后，才可单独提出状态变更；本文件本身不改变 `FIELD-01…06=TARGET_NOT_RUN` 或现场 `NOT_VERIFIED`。
